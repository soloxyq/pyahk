# 05 — 图像捕获与性能

> DXGI 零拷贝捕获 + HSV 模板匹配的实现细节。改捕获策略或检测算法时查这里。

## 1. 捕获栈

```
[屏幕] ──DXGI Desktop Duplication──► C++ 双缓冲区
                                         │
                                         ▼
                                   原子指针交换
                                         │
                                         ▼ ctypes 零拷贝映射
                            NativeGraphicsCaptureManager (Python)
                                         │
                                         ▼
                              BorderFrameManager.get_current_frame()
                                         │
                                         ▼
                              numpy.ndarray (H, W, 4) BGRA 只读快照
```

C++ 库源码在 `native_capture/`,Python 包装在 `torchlight_assistant/utils/native_graphics_capture_manager.py`。

### 关键技术点

1. **DXGI Desktop Duplication API**:Windows 8+ 的官方游戏级捕获 API,直接读 GPU 帧缓冲,不走 GDI(后者慢且会被全屏游戏屏蔽)
2. **双缓冲 + 原子指针**:C++ 端写入"后缓冲",原子交换指针给"前缓冲"。原子指针只解决缓冲发布；导出的 session API 仍由 native 全局锁串行化（DXGI/D3D11 immediate context、配置、stop/destroy 和注册表都不能并发访问）。
3. **ctypes 零拷贝**:C++ → Python 边界不复制字节,`np.ctypeslib.as_array` 得到的是**视图**
4. **帧快照所有权(Python 侧)**:`BorderFrameManager.get_current_frame()` **不**把上面那个视图交出去。
   视图指向 A/B 双缓冲,之后第二次取帧就会被原地覆写,而 `stop()` 会直接释放该内存 ——
   消费者(调度线程检测/OCR、GUI 预览)在锁外持有它必然撕裂、混帧,甚至 use-after-free。
   因此 `get_current_frame()` 返回 `_capture_lock` **锁内复制的快照**。

#### 快照契约(改检测代码前必读)

| 规则 | 说明 |
|------|------|
| 只读共享 | 复用窗口内多次调用拿到的是**同一个数组对象**;快照已 `setflags(write=False)`,原地写会当场抛 `ValueError`。需要可写数组请自行 `.copy()` |
| 复用窗口 | `min(max(10ms, 捕获间隔/2), 捕获间隔)`。窗口内不再触发 C++ 取帧 —— 同一轮决策看到同一画面 |
| 失效时机 | `stop()` / `pause_capture()` / `start_capture_loop()` 成功后都会作废快照;`running=False` 或 `paused=True` 时 `get_current_frame()` 返回 `None`(不返回暂停前的旧帧) |
| 第三方库 | 推理库可能对输入做原地预处理,递进去前先 `PaddleOCRManager._ensure_writable()` |

### 性能数据

| 操作 | 耗时 |
|------|------|
| C++ 单帧捕获 | ~5ms(DXGI 内部) |
| Python `get_current_frame()` 复用窗口内命中 | ~0(直接返回已有快照) |
| Python `get_current_frame()` 需要刷新 | 1 次全帧 memcpy(1080p ≈ 8MB) |
| 1080p 帧大小 | ~8MB BGRA |

## 2. 捕获模式

### 坐标契约（多显示器必读）

配置中的冷却、资源、OCR、minimap 与 `CaptureConfig.region` 均是 **Windows 虚拟桌面的物理像素绝对坐标**。副屏可以有负坐标；不要把某块输出的局部 `(0, 0)` 写入配置。

DXGI 内部只能复制一个 output，native 会把绝对区域减去该 output 的
`DesktopCoordinates.left/top` 后再裁剪；返回帧同时带有其绝对 `frame_rect`。`BorderFrameManager` 据此把配置坐标切回帧内坐标。区域必须完整落在当前 output，跨 output 的矩形会安全失败而不是悄悄裁到边缘。

窗口会在每次取帧前复查所属 `HMONITOR`；跨屏时重建该 output 的 duplication，旧屏帧不会继续返回。显示器模式的 `monitor_index` 是所有 DXGI outputs 的全局零基索引，**不是 adapter 索引**。

### 全屏 vs 区域

```python
config = CaptureConfig(
    target_window_handle=hwnd,
    capture_interval_ms=40,
    enable_region=False,        # True 时启用区域捕获
    region_x=0, region_y=0,
    region_width=1920, region_height=1080
)
```

`enable_region=True` 时,C++ 端只取指定矩形,数据量小,适合只关心一小块(如冷却图标聚集区)。矩形仍使用上节的虚拟桌面绝对坐标。
默认 `False` = 全屏,Python 端用 `get_region_from_frame(frame, x, y, w, h)` 切片。

### 窗口 vs 显示器

```python
CaptureConfig(target_window_handle=hwnd)        # 选择窗口当前所在 output；跨屏自动重建
CaptureConfig(capture_monitor=True, monitor_index=0)  # 固定显示器
```

游戏自动化通常用窗口模式；它是“选择窗口所在 output”的 Desktop Duplication，不是按窗口矩形裁图。窗口移动到另一块屏幕会切换 output；配置使用虚拟桌面绝对坐标，因此切换 output 时不需要做 output-local 原点换算，但游戏 UI 自身移动后仍应重新框选对应区域。

### 暂停与恢复

`pause_capture()` 调用 C++ `stop_capture()` 释放 GPU 资源,**不销毁 session**;`resume_capture()` 重启采集。

每个 Python wrapper 的 `cleanup()` 仅释放自己的 session；native 库以引用计数维护全局 D3D/DXGI 生命周期，临时模板捕获的清理不会销毁正在 RUNNING 的主捕获。

`MacroEngine` 在进入 PAUSED 状态时会暂停,极大节省 CPU(配合优先级按键暂停机制)。

## 3. HSV 模板匹配

### 为什么不用 OpenCV `matchTemplate`

- `matchTemplate` 慢(~10-50ms),且对光照/抗锯齿敏感
- HSV 像素级容差检测 0.3ms,且更鲁棒(色相比像素值稳定)

### 算法核心(`BorderFrameManager._compare_resource_hsv`)

```
1. 取当前区域 BGR → 转 HSV
2. 与模板 HSV 逐像素对比, 容差 (h_tolerance, s_tolerance, v_tolerance)
3. HSV 每个通道生成布尔匹配矩阵
4. AND 三个通道得到 pixel_match (布尔矩阵)
5. 沿垂直方向 sum, 每行统计匹配像素数
6. 行匹配像素 > 60% × 宽度 视为"该行有效"
7. 累计有效行数 / 总高度 = 匹配百分比
```

匹配百分比 ≈ 当前资源条的有效填充行占比。实现累计**全部**
有效行，不要误读为“只取自底向上的最长连续段”；这样可容忍资源条中间的遮挡。

### 对 HP 红色的特殊处理

红色在 HSV 中 H 跨越 0/180 边界(0-10 和 170-179 都是红),`_create_enhanced_color_mask` 用双区间或运算:

```python
h_match1 = abs(region_h - template_h) <= h_tolerance
h_diff_wrap = min(abs(region_h - template_h), 180 - abs(...))
h_match2 = h_diff_wrap <= h_tolerance
h_match = h_match1 | h_match2
```

### 容差经验值

| 场景 | h | s | v |
|------|---|---|---|
| 资源(HP/MP)模板 | 10 | 30 | 50 |
| 技能冷却 | 10 | 20 | 25 |
| 严格匹配(如选中状态) | 5 | 15 | 20 |

GUI 的 ColorAnalysisTools 提供可视化容差调节工具。

## 4. 三种资源检测对比

表中 rectangle/template/keras/tesseract 的历史数值来自 239 帧、HP+MP 共
478 次识别的基准(2025.10)。仓库保存的 `benchmark_results.json` 显示 rectangle
全部产出结果；在 468 个可与 OCR 数值比较的结果中，91.2% 的差值低于 5 个百分点。
这些耗时均为每帧完成 HP+MP 两项检测的总时间；产出率不等于识别准确率，
OCR 对比值也不是人工标注真值。
circle 与 Paddle 的数值是历史运行估计，当前
`performance_test/perf_full_benchmark.py` 不覆盖这两项，不能与 478 次结果混为一谈:

| 模式 | 算法 | 平均耗时 | 成功率 | 适合 |
|------|------|---------|--------|------|
| **rectangle**(推荐) | HSV 模板 + 行填充 | **0.262ms/帧（HP+MP）** | 100% 产出；91.2% 的有效对比差值 <5 个百分点 | 条形资源条(PoE2/Torchlight) |
| **circle** | HSV 模板 + 半圆掩码 | 历史估计 ~5ms | 当前脚本未测 | 球形资源条(D4) |
| **text_ocr / paddle** | PaddleOCR rec-only | 历史估计 CPU ~21ms / GPU ~6ms | 当前脚本未测 | 数字显示；F8 校验并锁定用户框选区域 |
| **text_ocr / template** | 自训数字模板匹配 | ~24.1ms/帧（HP+MP） | 98.3% | 具有匹配数字模板的显示样式 |
| **text_ocr / keras** | CNN | ~96.9ms/帧（HP+MP） | 98.5% | 需单独验证识别质量的可选引擎 |
| **text_ocr / tesseract** | Tesseract OCR | ~239.6ms/帧（HP+MP） | 99.0% | 独立可选引擎（不会自动从其他 OCR 引擎回退） |

> 在这批样本和机器上，三种 OCR 耗时约为 rectangle 的 92–916 倍；实际选择仍需验证游戏画面的误判率。

## 5. 帧缓存与一致性

### 单帧多检测(`SkillManager._prepare_frame_detection_cache`)

`check_cooldowns()` 每周期取**一帧**给所有技能用:

```python
def check_cooldowns(self):
    cached_frame = self._prepare_frame_detection_cache()
    if cached_frame is None:
        return
    for skill_name, skill_config in skills_to_check:
        self._try_execute_skill(skill_name, skill_config, cached_frame)
```

收益:N 个技能从 N 次 `get_current_frame()` 降为 1 次,且**所有技能基于同一帧时序一致**(避免技能 A 在 t1 帧就绪、技能 B 在 t2 帧不就绪的"滑动窗口"问题)。

### 帧使用统计

`SkillManager.get_frame_performance_stats()` 返回:
```python
{
    "total_frame_gets": 12345,
    "cached_frame_usage": 12300,
    "performance_ratio": 99.6  # 缓存命中率 %
}
```

## 6. 管理键期间的调度策略

当前设计**不再因管理键暂停 `UnifiedScheduler`**。暂停整个调度器会同时停掉
`resource_checker`,使 HP/MP 检测在管理键的前后 delay 或 hold 窗口中失效;
若 `managed_key_complete` 通知丢失,还会永久停在暂停态。

现在的职责划分:

```text
管理键按下
  → AHK 清空非紧急队列
  → delay_clear 窗口持续清理竞争动作,但放行 HP/MP
  → 宏解释器与技能持键进入抑制态
  → Python 调度器继续运行,资源检测不中断

最后一个管理键完成
  → AHK 自行解除抑制
  → ReconcileSkillHoldKeys() 补齐被推迟的持键
  → managed_key_complete 只用于 Python 日志/状态观察
```

特殊键同理:Python 只丢弃新的非紧急输入决策,AHK 仍放行紧急药剂和安全释放;
资源检测任务继续运行。真正的 PAUSED 状态才会暂停整个调度器并清空运行时输入。

若后续需要降低管理键窗口内的图像计算成本,应把资源检测与技能检测拆成独立调度域,
而不是再次暂停共享调度器。

## 7. 模板缓存(`BorderFrameManager._template_cache`)

F8 进 READY 时:
1. `MacroEngine._on_state_enter(READY)` 调 `border_manager.capture_once_for_debug_and_cache()` 取一帧
2. `ResourceManager.capture_template_hsv(frame)` 把 HP/MP 区域转 HSV 存到 `_template_cache["hp_region"]/["mp_region"]`
3. `BorderFrameManager.prepare_border()` 也把每个启用的冷却技能区域存为 `<skill_name>_cooldown`

后续 `_compare_resource_hsv` / `compare_cooldown_image` 都查这个缓存。

**模板从哪来**:就是 F8 那一刻的屏幕。所以:
- F8 必须在游戏正常状态(满 HP/MP/技能就绪)按
- 玩家死亡/技能 CD 时按 F8 会用错误模板,后续检测全错

当前 GUI 没有 RUNNING 期“重新截取模板”按钮。需重采时先按 F8 进入
STOPPED，确保游戏画面处于正确状态，再按 F8 重新完成 READY 准备。

### 内存上限

```python
self._cache_memory_limit = 50 * 1024 * 1024  # 50MB
```

超过时清最早的(目前未实现 LRU,只有 `_last_cache_cleanup` 时间戳)。HSV 模板很小,通常占用 < 1MB。

## 9. 常见性能陷阱

| 陷阱 | 表现 | 修法 |
|------|------|------|
| `cooldown_checker_interval` 太小(如 10ms) | CPU 100% | 调到 50-100ms,人眼无感差异 |
| `capture_interval` 太小(如 10ms) | CPU 高 + 帧重复 | 调到 30-50ms |
| 启用 text_ocr 但用 keras/tesseract 引擎 | 每周期 100-250ms | 改用 paddle(rec-only)或 template 引擎 |
| 多个技能配 ExecuteCondition=2 但 ConditionCoord 重复 | 同一像素读多次 | 当前没有共享条件配置；保留条件语义，后续可按帧缓存像素检测结果 |
| OSD 显示太多检测区域 | UI 卡顿 | DEBUG MODE 不要长开 |
