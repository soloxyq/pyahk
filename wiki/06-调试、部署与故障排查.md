# 06 — 调试、部署与故障排查

> 出问题先看这里。从日志位置到常见 BUG 排查路径,实用清单。

## 1. 调试日志开关

`debug_log.py` 三个 API:
```python
LOG_INFO("...")     # 总是输出
LOG_ERROR("...")    # 总是输出 + stderr
LOG("...")          # 只在 DEBUG=1 时输出(高频日志用)
```

启用 DEBUG 模式两种方式:
```bash
# 方式 1: 环境变量(进程级)
DEBUG=1 python main.py

# 方式 2: GUI 顶部"DEBUG MODE"复选框(运行时切换)
```

GUI 复选框还会:
- 启用 `dry_run_mode`(按键不真发,只记录)
- READY/RUNNING/PAUSED 时显示 `DebugOsdWindow`(技能/资源可视化)

## 2. OSD 窗口

### OSDStatusWindow(`status_window.py`)

主状态显示:READY/RUNNING/PAUSED 文字 + 颜色。RUNNING/PAUSED 且配置了 `boss_mode_hotkey` 时会附带 `BOSS:开/关`。点不到、不抢焦点(`WA_TransparentForMouseEvents` + `WA_ShowWithoutActivating`)。

窗口标题 `TorchLightAssistant_OSD_12345` —— **AHK 用这个标题查找窗口发事件**,改了的话同步改 `ahk_event_filter.py` 和 AHK 端的 `CurrentPythonWindow`。

### DebugOsdWindow(`debug_osd_window.py`)

DEBUG MODE 启用时显示。内容:
- 当前 HP/MP 百分比
- 各启用技能的实时匹配度 + 是否就绪
- 检测区域可视化(冷却小框、HP/MP 区域、条件检测点)
- dry_run 模式下的虚拟按键流

## 3. AHK 服务器调试

AHK 子进程启动时**不弹任何 GUI**(`gui1.Hide()`)。要调试它:

### 看 AHK 是否在跑

```bash
# Windows 任务管理器搜 "AutoHotkey64"
# 或 PowerShell:
Get-Process | Where-Object {$_.ProcessName -like "*AutoHotkey*"}
```

### 让 AHK 输出日志

`hold_server_extended.ahk` 默认无日志。要调试时,在关键位置加:

```ahk
; 临时调试: 写入文件
FileAppend "[" A_Now "] HandleManagedKey: " key "`n", "*"
```

或重启 TrayTip:
```ahk
; line 1062 原本注释了:
TrayTip("AHK输入系统已启动", "hold_server_extended.ahk", 1)
```

### 手动停 AHK 进程

Python 退出 = 调 `ahk_process.terminate()`。如果 Python 崩溃 AHK 残留:

```powershell
Stop-Process -Name "AutoHotkey64" -Force
```

或在 AHK 服务器界面右键托盘图标(默认隐藏,需要 `gui1.Show()` 临时调出)。

## 5. AHK 函数 global 完整性自检

历史踩坑:`ClearQueue` 漏写 global 声明 → PAUSED 看似清队列实际没清。定期跑:

```bash
python3 << 'EOF'
import re
with open('hold_server_extended.ahk') as f: lines = f.readlines()
key_fns = {
    'ProcessQueue': {'DelayUntil','DelayClearOthers','TotalQueueCount','QueueCounts',
                     'EmergencyQueue','HighQueue','NormalQueue','LowQueue',
                     'QueueStats','IsPaused','SpecialKeysPaused'},
    'ClearQueue': {'QueueCounts','TotalQueueCount',
                   'EmergencyQueue','HighQueue','NormalQueue','LowQueue'},
    'ExecuteAction': {'DelayUntil','DelayClearOthers'},
    'EnqueueAction': {'EmergencyQueue','HighQueue','NormalQueue','LowQueue','QueueStats'},
    'ClearNonEmergencyQueues': {'HighQueue','NormalQueue','LowQueue','QueueCounts','TotalQueueCount'},
}
fn_pat = re.compile(r'^([A-Z][a-zA-Z_]*)\([^)]*\)\s*\{')
cur, fn_globals, results = None, [], []
for line in lines:
    m = fn_pat.match(line)
    if m:
        if cur: results.append((cur, fn_globals))
        cur, fn_globals = m.group(1), []
    elif cur and line.strip().startswith('global '):
        for v in line.strip().replace('global ', '').rstrip(',').split(','):
            v = v.strip()
            if v: fn_globals.append(v.split(':=')[0].strip())
if cur: results.append((cur, fn_globals))
for fn, decl in results:
    if fn in key_fns:
        miss = key_fns[fn] - set(decl)
        print(f"{'OK' if not miss else 'MISS'}: {fn}  缺: {miss or '无'}")
EOF
```

## 6. 行尾(LF / CRLF)

仓库已加 `.gitattributes` 强制 `* text=auto eol=lf`。但 WSL 编辑器仍可能保存为 CRLF。

### 验证

```bash
# 看单文件
file <path>          # "Unicode text" 无 CRLF 标记 = LF; "with CRLF line terminators" = 坏

# 看是否有 trailing whitespace
git diff --check HEAD -- <path>

# 看真实改动规模(忽略行尾)
git diff --stat --ignore-space-at-eol HEAD
```

### 修复 CRLF

```python
# 用 Python 最稳(sed 在 WSL 偶尔静默失败)
import sys
for f in sys.argv[1:]:
    with open(f, 'rb') as fp: data = fp.read()
    if b'\r\n' in data:
        with open(f, 'wb') as fp: fp.write(data.replace(b'\r\n', b'\n'))
        print(f'fixed: {f}')
```

存为 `fix_eol.py`,然后 `python3 fix_eol.py path1 path2 ...`。

## 7. 常见 BUG → 排查路径

### BUG: 按 F8 没反应,主窗口没消失

**可能原因**:
1. AHK 没启动(F8 Hook 没注册)
2. F8 被其他程序占用(如 NVIDIA 录制)
3. Python 主窗口标题被改过,AHK 找不到

**排查**:
```bash
# AHK 在跑吗
ps -ef | grep -i autohotkey   # WSL 看不到 Windows 进程
# 改用 PowerShell: Get-Process AutoHotkey64

# F8 是否被 AHK 注册
python3 -c "
from hold_client import send_ahk_cmd
print('PING:', send_ahk_cmd('HoldServer_Window_UniqueName_12345', 1))
print('HOOK:', send_ahk_cmd('HoldServer_Window_UniqueName_12345', 8, 'F8:intercept'))
"
```

### BUG: 状态切到 RUNNING 但技能不发

**可能原因**:
1. `window_activation` 配错,目标窗口没激活,SendInput 发到错误窗口
2. `dry_run_mode` 仍开着(GUI 顶部 DEBUG MODE 打勾会自动开)
3. AHK 队列被 PAUSED 状态的旧 clear_queue(-1) 卡住

**排查**:
```bash
DEBUG=1 python main.py
# 观察日志:
# [AHK输入][DEBUG] send_key called with: q   ← 表示 Python 发出去了
# 没看到 = SkillManager 没调
# 看到 = AHK 收到但没发(看 dry_run / window_activation)
```

**模板未截**也常见。F8 必须在游戏正常状态(满 HP/MP/技能就绪)按,否则:
```
[ResourceManager] 未找到模板缓存: hp_region,请先按F8初始化
```

### BUG: HP 低了不喝药

**可能原因**:
1. `resource_management.hp_config.enabled=false`
2. `threshold` 设太低(如 10),实际不会跌到那么低
3. `cooldown` 还没过(`time.monotonic` 控制)
4. **序列模式下 resource_checker 漏注册**(2025 已修,B1)
5. detection_mode=text_ocr 但 OCR 引擎初始化失败

**排查**:
```python
# DEBUG=1 看周期日志
# [HSV检测] hp_region - 匹配详情: 区域大小=150x50, 填充行数=18/50, 匹配度=36.00%
# 36% < threshold(50) 应该触发
# 看下一行有没有 "已执行HP资源 - 按键: 1"
```

### BUG: 按住 A 不停发 f 键

**这不是 BUG,是设计意图**(强制移动 + 互动)。详见 [02-架构与通信](02-架构与核心概念.md) 的"设计意图"段。

按住 `force_move_hotkey` 时,非白名单、非 HP/MP 的自动 `SendPress` 会被替换成 `force_move_replacement_key`。如果某些自动键必须保留,显式写入 `stationary_mode_config.force_move_passthrough_keys`。

注意: `priority_keys.special_keys` 不会自动加入强制移动白名单。特殊键只表示“用户物理按下时透传并让自动系统让路”;白名单表示“强制移动期间程序自动发该键时不替换”。

如果不需要这个功能:把 `force_move_hotkey` 清空即可禁用强制移动监控。仅清空 `force_move_replacement_key` 不会禁用替换,AHK 收到空串会回到默认 `f`。

### BUG: 技能序列 "q,delay100,w" 中 w 不发

**可能原因**(2025 修复):
- 历史 BUG #2:序列展开后,delay 期间 `ClearNonEmergencyQueues()` 把 w 清掉了
- 已修:用 `DelayClearOthers` 标志区分管理键 delay(清队列)与普通 sequence delay(不清)
- 验证:`hold_server_extended.ahk` `ProcessQueue` 内 `if (DelayClearOthers && ...) ClearNonEmergencyQueues()` 应有 `DelayClearOthers &&` 前缀

当前通用宏模式不再依赖旧 `sequence_timer_interval`;若宏太快,请在 `macro_steps` 里显式加入 `delay` 步骤。

### BUG: 原地模式按技能键完全没反应

**可能原因**(2025 修复):
- 历史 BUG #2:`SendDirect` 对 `+1`(Shift+1)发送 `Send "{+1}"` 是非法 AHK 语法
- 已修:`SendDirect` 检查 `StrLen(key) > 1 && SubStr(key, 1, 1) = "+"` → `Send "+{" SubStr(key, 2) "}"`

### BUG: PAUSED 后恢复 RUNNING,旧技能动作残留爆发

**可能原因**(2025 修复):
- 历史 BUG:`ClearQueue` 没声明 `EmergencyQueue/HighQueue/NormalQueue/LowQueue` 为 global → 赋值 `[]` 实际创建局部变量,全局队列旧动作还在
- 已修:`ClearQueue` 顶部加齐 global 声明
- 验证:跑第 5 节的 global 完整性自检脚本

### BUG: TriggerMode=2 按住模式下,Space 闪避或 F8 退出后键卡住

**可能原因**(2025 修复 — 三层防御):
- **历史 BUG #1**:`release_key()` 走 normal 队列,会被 managed key 的 `delay_clear` 期间的 `ClearNonEmergencyQueues()` 清掉 → 游戏里键被永久按住
- **历史 BUG #2**:`SpecialKeysPaused` 期间 `ProcessQueue` 只扫每个队列队首,如果队首是普通 `press:*`,后面的 `release:*` 会被埋住
- **历史 BUG #3**:STOPPED 路径里 `clear_all_configurable_hooks()` 把 `~space` hook 注销后,AHK 永远收不到 Space up 事件 → `SpecialKeysPaused` 卡 true → 后续 `release:*` 被卡

**已修(三层叠加)**:
1. `release_key` 默认 `priority=0`(emergency 队列,绕过 `ClearNonEmergencyQueues` 与 `SpecialKeysPaused` 过滤)
2. `IsAllowedDuringPause(action)` 让 `release:*` 在 `SpecialKeysPaused` 期间也能透过(双保险)
3. `UnregisterHook(special)` 同步从 `SpecialKeysPressed` 删除该 key,若全空则 `SpecialKeysPaused→false` 并发 `special_key_pause:end` 给 Python(连带把 `_drop_non_emergency` 拉回 false);`ClearAllConfigurableHooks()` 末尾兜底再做一次

**验证**:`hold_server_extended.ahk` 内
- `IsAllowedDuringPause` 函数存在
- `ClearQueue(-1)` 内有 `DelayUntil := 0; DelayClearOthers := false; ActiveManagedKeys := Map()`
- `UnregisterHook(special)` 分支有 `SpecialKeysPressed.Delete(key)` 与 pause 状态归零
- Python 端 `ahk_input_handler.py` 的 `release_key` 调用 `command_sender.release_key(key, priority=0)`

### BUG: WSL 改完代码 git diff 显示 99 个文件

**症状**:你只编辑了 1-2 个文件,git status 却列出几十个 modified。

**原因**:WSL 把 LF 改成了 CRLF。

**修法**:第 6 节。

### BUG: AHK 进程崩溃不重启

**当前设计**:不做自动重启。AHK 是单点,崩了系统拒绝运行(见 docs/AHK_COMPLETE_ARCHITECTURE.md)。运行期命令发送失败时,`AHKInputHandler` 会探测子进程是否已退出,首次发现会发 `ahk_process_died` 事件,MacroEngine 延后切到 STOPPED 并告警。

边界:这不是空闲 watchdog。AHK 若在 READY/STOPPED 空闲时崩溃,要等下一次发送命令才会被发现。也没有 OS 级 `SendInput` 解卡兜底,AHK 已死时可能残留持久按住键。

**排查**:
1. PowerShell 看 Windows 事件查看器,搜"AutoHotkey64.exe"崩溃记录
2. 在 AHK 脚本里加 `try/catch` 包关键函数
3. 如需空闲秒级发现,再加主线程 QTimer watchdog；当前主线未启用

## 8. 性能问题排查

### CPU 高

```bash
DEBUG=1 python main.py
# 看 [统一调度器] 日志,几个间隔配置:
#   cooldown_checker_interval (默认 100ms)
#   capture_interval (默认 40ms)
#   resource check_interval (默认 200ms)
```

调大间隔(如 cooldown 100→200)立刻降 CPU。

### UI 卡顿

- 关掉 DEBUG MODE(OSD 渲染消耗大)
- 检查 `[事件总线性能]` 日志的 events/s,> 50 可能有事件风暴
- 看 `border_manager.start_capture_loop` 日志确认 capture_interval

### 帧率不稳

- C++ 捕获间隔 `capture_interval_ms`(C++ 内部) vs `BorderFrameManager.start_capture_loop(interval_ms=)`,确认一致
- DXGI 在某些笔记本会被独显/集显切换打断(`pause_capture` 时观察是否丢帧)

## 9. 部署清单

打包发布给非开发用户时:

1. **Python 环境**:用 `pyinstaller` 或同类工具打包 main.py,带上 `requirements.txt` 的所有依赖
2. **C++ 库**:`native_capture/capture_lib.dll` 必须和 .py 同目录
3. **AutoHotkey**:不打包,要求用户先装 AHK v2(`https://www.autohotkey.com/v2/`)
4. **配置路径**:在 `ahk_config.py` 把 `AHK_PATH` 改成 `r"C:\Program Files\AutoHotkey\v2\AutoHotkey64.exe"`(常见安装位置)
5. **Tesseract**(可选):用户用 text_ocr/tesseract 才需要,提示下载
6. **文档**:`AGENTS.md` + `wiki/01-快速入门.md` 给最终用户

## 10. 升级与回滚

升级 AutoHotkey 版本:
- AHK v2.0 → v2.1+: 检查 `hold_server_extended.ahk` 的 `#Requires` 行,语法可能微变

- 6.5 → 6.7+: `QAbstractNativeEventFilter` 签名稳定,但 `nativeEvent` 个别方法签名有变,看 `ahk_event_filter.py` 是否需要适配

回滚:
