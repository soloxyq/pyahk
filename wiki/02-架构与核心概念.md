# 02 — 架构与通信

> 改核心模块前必读。本文用最少篇幅讲清 5 件事:进程拓扑、状态机、WM_COPYDATA 协议、4 级队列、5 种 Hook 模式。

## 1. 进程拓扑

pyahk 是**双进程架构**:

```
┌─ Python 进程(PySide6 GUI) ─┐         ┌─ AHK 子进程 ─┐
│   决策、图像分析、UI         │         │  键盘拦截、  │
│                               │ WM_COPY │  队列处理、  │
│                               │←──DATA─→│  SendInput   │
└──────────────────────────────┘         └──────────────┘
       PID = main.py                         PID = AutoHotkey64.exe
                                             (Python 启动时 fork)
```

**职责切分原则**:
- Python:屏幕捕获 → 模板匹配 → 条件判断 → 决定要按什么键 → 发命令
- AHK:接命令入队 → 按优先级取出 → SendInput 给目标窗口
- AHK 还负责:拦截全局热键(F8/F7/F9/Z 等)→ 通知 Python

**为什么这样切**:Python 的 hook 库(pynput) 在 Windows 上有 suppress 卡死问题,AHK 的 `$` 前缀 hook 完美规避自拦截。Python 专心做"思考",AHK 专心做"动手"。

## 2. 状态机

```
        ┌──────────┐  F8   ┌────────┐   Z    ┌─────────┐
        │ STOPPED  │←─────→│ READY  │───────→│ RUNNING │←──┐
        │          │       │        │        │         │   │ Z
        └──────────┘       └────────┘        └─────────┘   │
              ▲                                  │  Z      │
              │                                  ▼         │
              │                              ┌────────┐    │
              └─── F8 (从任意非 STOPPED) ─── │ PAUSED │────┘
                                              └────────┘
```

定义在 `torchlight_assistant/core/states.py`:
```python
class MacroState(Enum):
    STOPPED = "stopped"
    READY = "ready"
    RUNNING = "running"
    PAUSED = "paused"
```

`MacroEngine.VALID_TRANSITIONS` 严格限制转换:STOPPED 只能去 READY,READY 只能去 RUNNING/STOPPED,等等。非法转换被 `_set_state()` 拒绝。

**每个状态的副作用**(进入时):
- **STOPPED**:清理所有动态 Hook(F8/F7/F9 永久根热键保留),停止 SkillManager/ResourceManager/BorderManager,但**不杀 AHK 进程**
- **READY**:先用 `arm_main` 在 AHK 原子关闸清场并标记主模式已武装,再注册 Z + 业务热键(原地模式键、强制移动键、BOSS 模式键、特殊键、管理键)、激活目标窗口并捕获一帧用于初始化模板缓存和 PaddleOCR 数字框锁定；全部准备成功后才开闸(F7/F9 不在此处注册,见下文"永久根热键")
- **RUNNING**:启动 BorderManager 循环捕获,SkillManager 启动统一调度器
- **PAUSED**:`clear_queue(-1)` 全清队列,所有 manager 暂停

**模式互斥** (`_prepared_mode`):
- `combat`:F8 进入,跑技能/资源
- `pathfinding`:F9 进入 READY 准备态,Z 进入 RUNNING 后才跑寻路
- 洗练(F7) 不进入状态机,仅在 STOPPED 状态可启动

### 永久根热键 vs 动态热键

`MacroEngine._setup_primary_hotkey()` 启动时永久注册 **F8 / F7 / F9**:
- F8:STOPPED ↔ READY
- F7:handler 检查 `_state == STOPPED` → 启动洗练; 非 STOPPED 则忽略
- F9:STOPPED 且洗练未运行 → 设 `_prepared_mode = pathfinding` 并转入 READY 准备态(`prepare_border_only`),`PathfindingManager` 实际启动要等 Z 触发 READY → RUNNING;非 STOPPED 且当前为 pathfinding → 停止(转 STOPPED);combat 模式或洗练运行中 → 忽略

这三个键即使进 STOPPED 状态也保留(AHK 端 `RegisterHook` 把它们排除在 `RegisteredHooks` 外,所以 `ClearAllConfigurableHooks` 不会清),保证用户随时可触发。

`_register_secondary_hotkeys()` 只在 READY 时注册 **Z + 业务热键**(原地模式键、强制移动键、BOSS 模式键、特殊键、管理键、RButton 等),进 STOPPED 时全部清掉。

## 3. WM_COPYDATA 通信协议

### 3.1 Python → AHK(命令)

入口:`hold_client.send_ahk_cmd_ex(window_title, cmd_id, param)`,首次查找窗口句柄后缓存
(实测 0.069ms 单次)。窗口消失时清缓存并在下一条命令重新查找；一次 `no_window`
失败不熔断,因此 AHK 脚本重启后可自行恢复。

命令使用 `SendMessageTimeoutW` 同步发送,超时 500ms,标志为
`SMTO_ABORTIFHUNG | SMTO_ERRORONEXIT`。刻意不使用 `SMTO_BLOCK`:Python/AHK 可能同时
同步发送 WM_COPYDATA,等待期间必须继续泵浦传入消息。发送前清空 Win32 last-error,
避免旧的 `ERROR_TIMEOUT` 污染本次结果。

返回值协议是 `1=成功`、`2=业务拒绝`、`0=未处理/默认窗口过程`。`0` 不能作为业务拒绝,
调用方必须能区分“AHK 明确拒绝”和“没有取得协议层结果”。

进程仍活着但命令超时时,Python 会熔断后续普通命令并进入延迟 STOPPED；`no_window`
不会熔断。STOPPED 的安全清理命令使用 `force=True` 穿透熔断,尤其
`set_accepting_actions(False)` 会在 AHK 端用一条消息原子完成关闸、清队、停宏和释放
全部持键。真挂死时最多额外等待一次 500ms；若 AHK 只是短暂停顿后恢复,这次清理可立即止血。
熔断不是永久状态：冷却 2 秒后下一次启动只发送一个串行 `PING` 探测，成功才解除熔断，
且绝不重放触发超时的业务命令。

`CMD_ACTIVATE` 只在接收栈内校验目标窗口,实际 `WinActivate` 由一次性 timer 异步执行。
AHK v2 默认 `SetWinDelay` 是 100ms,不能让这段固定等待占用同步命令的响应预算。

```python
# torchlight_assistant/config/ahk_commands.py
CMD_PING                       = 1
CMD_SET_TARGET                 = 2    # "ahk_exe game.exe"
CMD_ACTIVATE                   = 3
CMD_ENQUEUE                    = 4    # "priority:action"  e.g. "2:press:q"
CMD_CLEAR_QUEUE                = 5    # -1=全部, -2=非紧急, 0-3=单优先级
CMD_PAUSE                      = 6
CMD_RESUME                     = 7
CMD_HOOK_REGISTER              = 8    # "key:mode"  e.g. "F8:intercept"
CMD_HOOK_UNREGISTER            = 9
CMD_SEND_KEY                   = 10
CMD_SEND_SEQUENCE              = 11
CMD_SET_STATIONARY             = 12   # "true:shift_modifier" / "true:block_mouse"
CMD_SET_FORCE_MOVE_KEY         = 13
CMD_SET_FORCE_MOVE_STATE       = 14   # "true"/"false"
CMD_SET_MANAGED_KEY_CONFIG     = 15   # "key:target:delay[:hold_ms]"
CMD_CLEAR_HOOKS                = 16   # 清所有可配置 Hook(保留 F8/F7/F9)
CMD_SET_FORCE_MOVE_REPLACEMENT_KEY = 17
CMD_SET_PYTHON_WINDOW_STATE    = 18   # "main"/"osd",决定 AHK 往哪个窗口发事件
CMD_BATCH_UPDATE_CONFIG        = 19   # "hp_key:1,mp_key:2,stationary_type:..."
CMD_SET_SEND_MODE              = 20   # "direct"(SendInput) / "control"(ControlSend)
CMD_SET_FORCE_MOVE_PASSTHROUGH_KEYS = 21  # "RButton,space"
CMD_SET_MACRO_STEPS            = 22   # AHK 端宏步骤 line protocol: "type:data\n..."
CMD_START_MACRO                = 23   # 启动 AHK 端宏循环
CMD_STOP_MACRO                 = 24   # 停止宏循环并释放宏持键
CMD_SET_SKILL_HOLD_KEYS        = 25   # 声明 TriggerMode=2 期望持键集合(空=全部释放)
CMD_SET_ACCEPTING_ACTIONS      = 26   # "false"=原子停止屏障;"true"=开闸;"arm_main"=关闸清场后武装主模式

```

> **AHK 端必须同步**:`ahk_commands.ahk` 与 `torchlight_assistant/config/ahk_commands.py` 的 ID 必须一一对应。新增命令时两处都要改。

### 3.2 AHK → Python(事件)

AHK 用 `SendEventToPython(event)` 发,目标窗口根据 `CurrentPythonWindow`(由 CMD_SET_PYTHON_WINDOW_STATE 控制)决定:
- `STOPPED` 状态 → main 窗口(`TorchLightAssistant_MainWindow_12345`)
- `READY/RUNNING/PAUSED` → OSD 窗口(`TorchLightAssistant_OSD_12345`)

反向事件同样使用 `SendMessageTimeoutW`,但超时仅 50ms。这个预算成立的前提是 Python
原生窗口过程只做解析和 signal emit；`AHKInputHandler` 使用显式 `Qt.QueuedConnection`,
READY 初始化、UI 配置采集、EventBus handler 等业务逻辑在窗口过程返回后的 Qt 事件循环执行。

失败策略按事件性质区分:

- `monitor_key_down/up` 与 `special_key_pause:start/end` 按状态通道合并为最新值,失败后
  共享通道退避 1 秒并由 100ms timer 补发。
- `intercept_key_down`、special/managed 边沿等不可合并事件先进入 64 项有界 FIFO。
  普通业务边沿软上限为 60,其余 4 项专门保留给 F8;超过软上限的普通边沿直接丢弃,
  避免 GUI 恢复后执行过期用户意图。F8 在绝对满时可驱逐非 F8 项,活跃主模式的 stop-only
  F8 还会作废旧运行世代的边沿。Hotkey 回调只入队并立即返回。timer 严格 FIFO 发送；
  超时保留队首并指数退避，成功才出队。
  线上载荷用 `evt:<AHK-session>:<seq>:<原事件>` 信封，Python 按 `(session, seq)` 去重，
  因此 SendMessageTimeoutW“接收方已处理但发送方超时”后的重试不会重复切换状态。
  键盘自动重复由 AHK 端按下状态去重
  (配对注册 `$key up` 复位;up 边沿丢失时 1.1s 时间窗兜底自愈,不会永久变死键)。
  滚轮键(WheelUp/Down/Left/Right)不参与去重:up 变体注册后永远不触发(实测),
  且滚轮无自动重复,每个刻度都是独立动作,必须全部发出。
- 主状态机从 READY 准备一开始就设置 `MainModeArmed`，不依赖首个动态 Hook 是否已经注册；
  因而准备期间的物理 F8 也被解释为 stop-only，而不会再次触发 STOPPED → READY。
  若启动用的 F8 此时仍物理按住，`MainModeF8AwaitRelease` 会抑制同一次长按的自动重复；
  永久 up Hook 正常解除，安全桌面吞掉 up 时由临时 25ms 物理键态轮询确认释放后自愈。
- 活跃或已武装主模式中的物理 F8 是上述“只入队”的安全例外：AHK 先建立本地 stop latch，原子
  关闸、清队、停宏并释放持键，再把 `f8_stop` 放入可靠 FIFO。latch 存在时任何迟到的
  `SET_ACCEPTING_ACTIONS(true)` 或 `arm_main` 都会被拒绝；只有 STOPPED 完整清掉动态 Hook
  并清除 `MainModeArmed` 后才解除。
  F8 同时作废尚未发送的旧世代边沿，停机之后新产生的人工事件仍按顺序保留。
- `stats` 是纯观测,失败直接丢弃且不武装共享退避门；失败后静默 2 秒，且有可靠/状态
  待发事件时跳过本轮统计，避免 GUI 卡顿期间反复占住 AHK 主线程。

Python→AHK 的 WM_COPYDATA 处理栈内只登记待发状态,不做同步反向发送。进入 STOPPED
清理动态 Hook 时,AHK 直接归零 monitor/special/force-move 状态并清空待补发 Map；Python
同样本地复位 force-move 与 special 生产抑制,旧 down 不会跨到下一轮运行后迟到。

Python 侧由**全局**事件过滤器接收:
```python
# torchlight_assistant/core/ahk_event_filter.py
class AHKEventFilter(QAbstractNativeEventFilter):
    def nativeEventFilter(self, eventType, message):
        # 解析 WM_COPYDATA → 通过 ahk_signal_bridge 发信号
        # 不消费消息,允许窗口默认过程继续
```
在 `main.py` 创建 QApplication 后立刻 `app.installNativeEventFilter(...)`,保证 attach 到 app 防 GC。

> 历史:之前 main_window 和 OSD 各自实现 nativeEvent 接收,有重复代码和潜在的"同一事件被处理两次"的风险。2025 重构改为单一接收点。

业务事件格式仍是 `event_type:data`；可靠边沿在线路上可带上述 `evt` 信封，接收层解包后
再进入以下既有路由:

| 事件 | 触发场景 | data |
|------|---------|------|
| `intercept_key_down` | 拦截型热键(F8/F7/F9/Z 等)按下 | 键名 |
| `special_key_down` / `_up` | 特殊键(Space)按下/释放;物理 key-up 与 `_up` 均立即发生 | 键名 |
| `special_key_pause` | 特殊键引发的自动输入暂停状态切换;`end` 可按配置延后 | `start`/`end` |
| `managed_key_down` | 管理键(E)按下 | 键名 |
| `managed_key_complete` | 管理键完成(delay+按键已发完) | 键名 |
| `monitor_key_down` / `_up` | 监控键(强制移动键 A) | 键名 |

事件路由:`AHKEventFilter` → `ahk_signal_bridge.ahk_event` Signal →
`Qt.QueuedConnection` → `AHKInputHandler._on_ahk_event` →
`event_bus.publish(event_type, ...)` → `MacroEngine` 各 handler。

## 4. 5 种 Hook 模式(AHK 侧)

由 `CMD_HOOK_REGISTER` 注册时指定模式:

| 模式 | AHK 前缀 | 拦截 | 释放事件 | 用途 | 例 |
|------|---------|------|---------|------|-----|
| **intercept** | `$` | ✅ 完全拦截(含 up) | ❌(up 仅本地去重) | 系统热键、技能键 | F8/F7/F9/Z/原地模式键 |
| **priority**(管理键) | `$` | ✅ 完全拦截 | ❌ | 拦截后映射+加 delay,程序代按 | RButton 闪现 / E → Shift |
| **special** | `~` | ❌ 透传 | ✅ | 状态监控,按住及可选松开保护期内抑制非紧急自动输入 | Space 闪避 |
| **monitor** | `~` | ❌ 透传 | ✅ | 仅状态跟踪 | 强制移动键 A |
| **block** | `$` | ✅ 完全屏蔽 | ❌ | 禁用某键 | 极少用 |

**`$` 前缀的关键作用**:防止 AHK 自己发的 SendInput 被自己的 hook 再次拦截(自拦截)。这是 Python pynput 时代的核心痛点,AHK 用 `$` 完美解决。

## 5. 4 级优先队列

定义在 `hold_server_extended.ahk` 顶部:

```ahk
global EmergencyQueue := []   ; 0 - 紧急(HP/MP 药剂、管理键 delay、TriggerMode=2 按住模式 release)
global HighQueue := []        ; 1 - 高(优先级技能)
global NormalQueue := []      ; 2 - 普通(常规技能/序列)
global LowQueue := []         ; 3 - 低(UI/拾取/辅助)
```

`SetTimer(ProcessQueue, QUEUE_TICK_MS)` 每 tick 调度一次,**每 tick 最多执行一个动作**。
`QUEUE_TICK_MS = 15`(实际约 15.8ms,原因见下面的"吞吐预算")。

### 取队规则

| 系统状态 | Emergency | High/Normal/Low |
|---------|-----------|-----------------|
| 正常运行 | 优先取 | 按优先级取 |
| `IsPaused=true`(用户 Z 暂停) | **仍取** | 暂停 |
| `SpecialKeysPaused=true`(Space 按住或松开保护期) | **仍取** | **只取安全动作**(`IsAllowedDuringPause`:HP/MP 紧急药剂 OR `release:*` 释放动作,后者防止 TriggerMode=2 按住键卡死) |
| `ManagedDelayUntil > 0`(管理键独占窗口,`delay_clear:`) | 只放行 HP/MP 药剂 | **被清空** |
| 某队列队首 `notBefore` 未到(普通 delay) | 不受影响 | **只挡那一条队列**,其余照常 |

> **两种延时,两种作用域(2026-08 重构)**:
> - **普通 delay(序列内 `delay:N` / 裸 `delay:N`)= 按队列**:转成本队列队首的 `seqrun:` 等待项
>   (`notBefore` 时间戳),`NextToExecuteQueueName()` 跳过未到期的队列 —— low 的 `delay:100`
>   不再压住 high 技能,优先级在 delay 面前恢复成立。尾部 delay(如 `q,delay100`)留**空哨兵**
>   `seqrun:` 占住队首,防止间隔语义蒸发;哨兵到期出队即完成,不重置延时。
>   emergency 队列不支持普通 delay(救命动作永不等待,delay 被忽略)。唯一例外是
>   `mouse_click_at:x,y,hold_ms` 生成的不可丢 LButton release，它用本优先级 `notBefore`
>   保持鼠标；尚未到期时后来的 HP/MP 可越过它执行。
> - **`delay_clear:`(管理键专利)= 仍是全局**:设 `ManagedDelayUntil`,窗口内清空非紧急队列,
>   保证管理键独占(E 键闪避/强力技)。这是刻意保留的全局闸门,不是遗漏。
>
> **ManagedDelayUntil 期间的 emergency 特例**:窗口内扫描 emergency 队列,只放行 `IsEmergencyAction()` 识别出的 HP/MP 药剂,避免独占窗口压住救命药。`release:*` 不提前放行,防止管理键 hold 序列被打乱。
>
> **`ClearQueue(-1)` 同步重置 ManagedDelayUntil/ActiveManagedKeys**:全清队列后保留旧独占窗口语义不干净,残留窗口会把 PAUSED→RESUME 时新入队的 `hold:N` 用 `ClearNonEmergencyQueues()` 清掉,造成按住模式 stuck。所以 `ClearQueue(-1)` 必须把它们也归零。

### sequence = 一个队列决策

`EnqueueAction(priority, action)` 拦截 `sequence:` 类型,**只规范化,不展开成多个队列项**:
```
sequence:q,delay100,w
  ↓ 规范化(仍是 1 个队列项)
sequence:press:q,delay:100,press:w
  ↓ ProcessQueue 每 tick 推进一个原子,剩余部分放回队首
tick1: press:q   → 队首变成 seqrun:delay:100,press:w
tick2: delay:100 → 队首变成 seqrun:press:w(带 notBefore = now+100,只挡本队列)
到期后的 tick: press:w
```
序列内 delay 走按队列 `notBefore` 等待,**没有同步 Sleep 阻塞**,也不再占用全局闸门。

⚠️ **为什么不展开**:一次 sequence 是**一个决策**,原子之间有因果关系,必须同生共死。
展开成 N 个队列项时有两个实测到的失效面:
- 后续任何普通入队都会按"丢最旧"从中间裁掉连招的前半段(20 步序列入队后再来一个普通动作,队头就从 k1 变成 k6);
- 整个展开在同一次 WM_COPYDATA 里完成、`ProcessQueue` 一个也排不出去,所以超过预算的长连招在**零过载**时就自己吃掉前半段。

作为单个队列项则不可能出现半截连招:要么整条被丢,要么按序走完。
开打之后剩余部分标记为 `seqrun:`,进入**不可丢**集合 —— 打一半停手比迟发整条更糟。

⚠️ 仍要记住 **1 变 N 的放大**:生产侧按"一个技能一次调度"计费,消费侧按"一个原子一个 tick"计费。
所以预算按**原子**算(见下)。

### 吞吐预算(实测,不是估算)

数字全部来自 `tests/test_ahk_queue_throughput.py` —— 它把真实的 `EnqueueAction`/`ProcessQueue`
逐字抽取出来跑在 AutoHotkey.exe 里,所以不会与实现漂移。

| 量 | 值 | 来源 |
|----|----|------|
| 执行上限 | **≈63 动作/秒** | `SetTimer(ProcessQueue, QUEUE_TICK_MS=15)` × **每 tick 最多 1 个动作** |
| 序列放大 | `q,w,e` = **1 个决策 / 3 个原子** ≈ 47ms | 每 tick 推进一个原子 |
| 队列预算 | `MAX_PENDING_ATOMS = 16`(**全局**,仅非紧急) | 预算 = 延迟上限:16 × 15.8ms ≈ **250ms** |
| 过期丢弃 | `STALE_MS = 500` | 出队时真实等待 ≥ 500ms(单调墙钟)的可丢动作直接丢弃 |

⚠️ **定时器周期不能凭直觉挑**。Windows 消息定时器粒度 ~15.6ms,`SetTimer` 会向上凑到整数个系统 tick。墙钟实测:

| 请求 | 实际周期 | 动作/秒 |
|------|---------|--------|
| 20ms | 31.6ms | 31.7 | ← 旧值,凑成 2 个系统 tick,白白浪费一半 |
| 16ms | 25.0ms | 40.0 |
| **15ms** | **15.8ms** | **63.3** | ← 现值,1 个系统 tick |
| 10/5/1ms | ~15.9ms | ~63 | 触底,再小也没用 |

**生产侧没有背压**:`check_cooldowns` 每 100ms 对每个"图标就绪"的冷却技能各入队一次;
`TriggerMode=0` 定时技能则**无条件**按 Timer 入队。仓库里现成配置的最大生产速率:

| 配置 | 最大生产 | 旧上限 31.7/s | 新上限 63/s |
|------|---------|--------------|------------|
| `d4灵巫.json` | 55.9/s | ❌ 永久过载 | ✅ |
| `last.json` | 37.3/s(4 个定时技能,无条件) | ❌ 永久过载 | ✅ |
| `d4_magic.json` / `d4.json` | ~32.5/s | ❌ 临界 | ✅ |
| 其余(`default` / `poe2*` / `tors10` …) | ≤ 28.6/s | ✅ | ✅ |

修复前的后果(实测):生产 100/s 跑 10 秒 → 积压 500 项,正在打出去的是 **10 秒前**决策的按键,
且随时间线性恶化,不报任何错。用户看到的只是"技能乱放",会一直去调技能配置。

现在的处理:

0. **提高上限**:`QUEUE_TICK_MS` 20 → 15,吞吐 31.7/s → 63.3/s(见上表)。仍是每 tick 一个动作,
   按键间距只是从 31.6ms 变成 15.8ms,不会出现"同一毫秒连发两个键"。
1. **全局原子预算**:三条非紧急队列**合起来**的待发原子超过 `MAX_PENDING_ATOMS` 就丢**最旧**的
   可丢动作 —— ARPG 里过期的决策毫无价值,最新决策才反映当前局面。
   实测积压稳定在 16 项、排队延迟恒 ≤255ms。

   ⚠️ 预算必须是**全局**的:出队是严格优先级的(high 空了才轮到 normal),按队列各限 16 的话
   三条队列能同时积压 48 项、低优先级要等 ~750ms —— "≤250ms" 就只在单一优先级下成立了。

   ⚠️ 预算按**原子**算而不是队列项:一个 20 原子的连招只占 1 项却要 20 个 tick,
   按项算的话 16 项 ≈ 5 秒,上限名存实亡。

   ⚠️ 两类豁免(不计入预算、也不会被丢):
   - **每条队列队首的 seqrun:**(已开打的在飞序列)。被更高优先级抢占时它滞留在自己
     队列的队首,不同优先级可以**同时**各有一条;只豁免全局队首的话,被抢占那条的剩余
     原子会把预算永久顶爆(两条都不可丢,无法收敛,所有新动作一到就被丢)。
     结构不变量:seqrun 由 PushFrontAction 放回位置 1、第二条序列在它后面出不了队,
     故**每条队列最多一条**,豁免总量 ≤ 3 条 × 用户配置的序列长度,有界。
   - **全局队首**(下一个要执行的决策):一条长连招本来就要那么多 tick,
     把它算进预算会让"配了长连招却永远放不出来"。

   实际在飞上界 = 预算 + 全局队首 1 个决策 + ≤3 条已开打序列的剩余(长度由用户配置)。
2. **哪些绝不丢**:`release:` / `cleanup:` / `notify:` / `delay_clear:` 是**状态恢复或控制**动作,
   丢弃后果是持久的 —— 丢 `release:` = 游戏内卡键(只能重启客户端),
   丢 `cleanup:` = 该管理键此后永远点不出来,丢 `delay_clear:` = 管理键独占语义失效。
   整条队列都是这类动作时**宁可超深也不丢**。紧急队列(HP/MP 保命)同样不设上限。
   另外**最新到达的动作永不被丢**:队头堆满不可丢动作时,唯一"可丢"的就是刚到的那个,
   丢它会让策略从"丢最旧"整个翻转成"丢最新"。
3. **过期丢弃(按项计龄)**:预算管得住"队列多长",管不住"多久轮不到"。严格优先级下,
   高优先级持续生产时低优先级会一直排不上,某天高优先级一空就打出几十秒前的决策。

   年龄**绑在每个队列项上**(入队时记录 `MonotonicMs()`,即 GetTickCount64 单调毫秒,
   含系统休眠时间),判定在**出队时**做:真实等待 ≥ `STALE_MS`(500ms)且可丢 →
   丢弃换下一个。不用"调度 tick 数"计:tick 只在定时器成功触发时才走,系统休眠或
   AHK 线程被长时间阻塞后恢复,按 tick 算会把真实等了几秒的动作当成"年轻"照常执行。
   一个 tick 仍最多**执行**一个动作,丢弃不发键、连丢多个不影响节奏。

   ⚠️ 时钟**不能**用 `A_TickCount`:它是 32 位 GetTickCount,约 49.7 天回绕 ——
   回绕瞬间 now - at 变成巨大负数,过期判定失效、通知节流冻结、`ManagedDelayUntil` /
   `MacroDueTime` 卡死。全文件统一走 `MonotonicMs()`(GetTickCount64 无回绕),
   由 `test_ahk_clock_is_gettickcount64_not_a_tickcount` 静态守卫禁止裸用。

   ⚠️ 不能按队列计数(第一版就是这么错的,两个实测错误):
   - 清队列不重置计数 → PAUSED 后新入队的动作"继承"旧年龄,等 1 tick 就被丢;
   - 计数只描述队首 → 丢掉前两个后清零,排在后面、等了 64 tick 的第 3 个照样被执行。

   语义提示:年龄是"真实等了多久"(墙钟毫秒,含 delay 期间)。被长 delay 或
   长连招压过 500ms 的普通动作会被丢弃而不是迟发 —— 这正是策略本意:过期决策没有价值。
   不可丢动作(release/cleanup/seqrun 等)不受影响,再老也照常执行。
4. **可见化**:丢弃会经 `queue_drop` 事件上报到 Python 并 `LOG_ERROR`,事件带
   `overload=`(预算裁剪)与 `expired=`(等待过期)两个**分开的累计计数** ——
   原因不同、诊断建议也不同,混成一条"入队速度超上限"会让"只是配了个长 delay"的
   用户去调根本没问题的技能生产率。(AHK 端节流到每秒最多一条,
   被节流时保留待发标志、下一 tick 重试,避免短促过载一条日志都没有)。
   `SendStatsToPython` 已修活(2026-08):AHK 每秒主动推送一次 `stats:` 事件,
   `e/h/n/l` 是**实时**队列深度(QueueCounts),`p/d/x` 是累计 处理/过载丢弃(`d=`)/
   等待过期(`x=`)。Python 端(main_window)在 RUNNING/PAUSED 时把它压成 OSD 的
   一行紧凑文本(丢弃计数零时不展示)。旧的 `get_stats()` 请求路径把字符串当命令 ID
   发送、从未工作过,已删除 —— 统计只推不拉。

> 通知为什么推迟到 `ProcessQueue` 发:丢弃发生在 `EnqueueAction`,而它常在 WM_COPYDATA 处理中执行 ——
> 此刻 Python 正在 `SendMessageTimeoutW` 里等这条消息返回。双向通信刻意不使用
> `SMTO_BLOCK`,因此可以处理交叉 WM_COPYDATA；过载通知仍推迟到定时器上下文,
> 避免在命令处理栈内引入不必要的嵌套事件。
> 因此只置 `PendingOverloadNotify` 标志,由定时器上下文的 `ProcessQueue` 下一 tick 发出。

**已解决(2026-08)**:旧的全局 `DelayUntil` 会让 low 的 `delay:100` 连 high 技能一起压住
(优先级在 delay 面前不成立)。现改为按队列 `notBefore`,由
`test_low_priority_delay_no_longer_blocks_high_priority` 等 4 个测试钉住新语义。
注意语义变化:序列 `q,delay100,w` 的**间隙里其他队列可以插入动作**(这正是修复目的);
需要间隙独占的场景应使用管理键(`delay_clear:` 仍是全局独占)。

**边界说明**:实际在飞上界 = `MAX_PENDING_ATOMS` + 全局队首 1 个决策 + ≤3 条已开打
序列的剩余原子(每优先级最多一条,长度由用户配置)。单原子动作时就是 17 项 ≈ 255ms;
配了长连招时,连招执行期间上界相应变大 —— 这是用户配置决定的执行时间,不是排队延迟。

### AHK 端通用宏解释器

`sequence_enabled=true` 的通用宏不再由 Python 调度器逐步执行。流程是:

1. Python 从 `global.macro_steps` 读取步骤(`down/up/press/delay`),通过 `CMD_SET_MACRO_STEPS=22` 下发给 AHK。
2. READY→RUNNING 时 Python 发 `CMD_START_MACRO=23`。
3. AHK `MacroTick` 以 5ms **轮询预算**检查宏状态机并顺序循环;它不是保证的步间隔
   (Windows timer 会按系统粒度量化)。只有显式 `delay` 步骤通过 `MacroDueTime` 定义等待。
4. PAUSED/STOPPED/配置切换时 Python 发 `CMD_STOP_MACRO=24`,AHK 端按 LIFO 释放仍按住的宏键。

这条路径独立于 4 级队列和所有延迟闸门,因此 `down` 与 `up` 不会因为 normal/emergency 队列优先级交错而乱序。

## 6. 设计意图(易被误判为 BUG)

| 行为 | 真相 |
|------|------|
| 强制移动键(默认 A)按住时,非白名单/非 HPMP 的自动 `SendPress` 被替换为 `f` | 边跑边互动:角色靠近装备/NPC 自动捡取/对话;白名单键和 HP/MP 正常发送 |

## 7. AHK 函数 global 完整性检查脚本

AHK v2 函数内对变量赋值会自动定为 local,**除非顶部 `global` 声明**。这是历史踩坑点(`ClearQueue` 漏声明导致 PAUSED 实际没清队列;`CMD_PAUSE` 漏声明 `IsPaused` 让暂停闸门从来没生效过)。

> ✅ **已自动化**:`tests/test_ahk_global_scope.py` 会扫出所有顶层全局,再逐个函数检查"赋值了但没声明"的情况(`Map[key] := v` 这类索引赋值是读取,已排除),覆盖整个文件而不是一张硬编码名单。直接 `python tests/test_ahk_global_scope.py` 即可。
>
> 下面这份脚本是它的前身,只覆盖固定几个函数,保留作参考:

```bash
python3 << 'EOF'
import re
with open('hold_server_extended.ahk') as f: lines = f.readlines()

key_fns = {
    'ProcessQueue': {'ManagedDelayUntil','TotalQueueCount','QueueCounts',
                     'EmergencyQueue','HighQueue','NormalQueue','LowQueue',
                     'QueueStats','IsPaused','SpecialKeysPaused'},
    'ClearQueue': {'QueueCounts','TotalQueueCount',
                   'EmergencyQueue','HighQueue','NormalQueue','LowQueue'},
    'ExecuteAction': {'ManagedDelayUntil'},
    'EnqueueAction': {'EmergencyQueue','HighQueue','NormalQueue','LowQueue','QueueStats'},
    'ClearNonEmergencyQueues': {'HighQueue','NormalQueue','LowQueue','QueueCounts','TotalQueueCount'},
}
fn_pat = re.compile(r'^([A-Z][a-zA-Z_]*)\([^)]*\)\s*\{')
cur, fn_globals, results = None, [], []
for line in lines:
    m = fn_pat.match(line)
    if m:
        if cur: results.append((cur, fn_globals))
        cur, fn_globals = m.group(1), []
    elif cur and line.strip().startswith('global '):
        for v in line.strip().replace('global ', '').rstrip(',').split(','):
            v = v.strip()
            if v: fn_globals.append(v.split(':=')[0].strip())
if cur: results.append((cur, fn_globals))

for fn, decl in results:
    if fn in key_fns:
        miss = key_fns[fn] - set(decl)
        print(f"{'OK' if not miss else 'MISS'}: {fn}  缺: {miss or '无'}")
EOF
```

## 8. 数据流总览

```
[屏幕] ──DXGI──► [C++ 共享内存] ──ctypes──► BorderFrameManager.get_current_frame()
                                                    │
                                                    ▼
                              SkillManager.check_cooldowns(frame) / check_resources(frame)
                                                    │
                                                    ▼
                              decision: 该按 q? 该喝 HP?
                                                    │
                                                    ▼
                              AHKInputHandler.execute_skill_high("q") / execute_hp_potion("1")
                                                    │
                                                    ▼
                              AHKCommandSender.send_key("q", priority=1)
                                                    │
                                                    ▼ WM_COPYDATA
                              hold_server.EnqueueAction(1, "press:q")
                                                    │
                                                    ▼ ProcessQueue (~15.8ms)
                              SendPress("q") → SendInput
                                                    │
                                                    ▼
                                                 [游戏窗口]
```

事件反向:
```
[键盘 F8] ──Hook──► HandleInterceptKey("F8") ──WM_COPYDATA──►
  → AHKEventFilter.nativeEventFilter → ahk_signal_bridge.ahk_event.emit
  → AHKInputHandler._on_ahk_event → event_bus.publish("intercept_key_down", key="F8")
  → MacroEngine._handle_ahk_intercept_key → publish("hotkey:f8_system_toggle")
  → MainWindow 采集当前 GUI 配置 → publish("ui:sync_and_toggle_state_requested", full_config)
  → MacroEngine._handle_f8_press(full_config) → _set_state(READY)
```

STOPPED 状态下,物理 F8 与界面上的“隐藏界面并启动”按钮共用上述入口。因此即使用户
尚未点击“保存配置”,本次运行也会使用当前控件值；F8 只同步运行态,不会自动覆盖磁盘文件。
从 READY/RUNNING/PAUSED 停止时则由引擎直接处理,不读取 GUI,确保控件异常不会阻断 F8 停机。
READY 采用两阶段入口：AHK 先原子关闸清场并设置 `MainModeArmed`，Python 完成 Hook、窗口激活、
捕获/OCR 准备后才开闸。后一条路径在通知 Python 前已经由 AHK 本地 stop latch 完成止血；即使 Qt 主线程正阻塞，
游戏也不会继续收到宏、队列或持键输入。若首次 Hook 清理只完成一部分，后续 `f8_stop`
会在 STOPPED 重跑幂等清理，而不是把停机意图误当成启动。

## 9. 线程模型

| 线程 | 职责 |
|------|------|
| Qt 主线程 | UI、WM_COPYDATA 接收(过滤器在主线程跑)、状态切换 |
| `UnifiedScheduler` 线程 | 单线程串行调度所有定时任务(`monotonic` + `heapq`) |
| `BorderFrameManager` 内线程 | C++ 捕获回调线程(可选,目前帧拉取由调度器触发) |
| `EventBus` 线程池 | `publish_async` 用,`max_workers=6`,有递归保护 + 并发上限 |
| `SimpleAffixRerollManager` / `PathfindingManager` | 各自独立线程(被洗练/寻路使用) |
| AHK 进程内 | `SetTimer(ProcessQueue, QUEUE_TICK_MS)` + Hook 回调 |

跨线程通信全部走 EventBus 或 SignalBridge,避免直接持有锁跨线程。
