# 04 — 配置 JSON Schema

> 配置文件字段权威清单。改 GUI 或加新功能开关前查这里。

## 文件位置

JSON 文件放在仓库根目录。首次启动加载 `default.json`；之后优先恢复
`.pyahk_state.json` 记录的上次成功加载/保存配置，记录不可用时再回退
`default.json`。游戏专用配置:
- `default.json` — 默认模板
- `d4.json` / `d4_druid.json` / `d4_magic.json` — Diablo IV
- `poe2_锐眼.json` / `POE2_amazon.json` — 流放之路 2
- `tors10.json` — Torchlight Infinite
- `notepadtest.json` — 测试用

切换配置:GUI 顶部 "加载配置" 按钮。

配置文件必须是标准 JSON：`NaN` / `Infinity`（含指数溢出成非有限数）会在
加载或保存边界被拒绝。布尔开关只把 JSON 字面量 `true` 当作开启，字符串
`"false"` 不会因为 Python truthy 而误启用输入生产者。GUI 会保留尚不认识的
枚举/扩展字段以便向前兼容，但运行时对未知输入模式、技能触发/条件模式、资源
检测模式和原地模式均 fail-closed，不会悄悄映射成一个现有可执行模式。
本文代码块为字段说明，使用了 `//` 注释和 `{ ... }` / `[...]` 省略符，不能原样
保存；实际配置必须去掉这些说明性内容后才是标准 JSON。


## skills

技能配置字典,key 是技能名(`Skill1`-`Skill8` 等任意字符串)。

```json
"Skill1": {
  "Enabled": true,                  // 是否启用
  "Key": "1",                       // 主按键(支持序列 "delay50,1,delay100,2")
  "Priority": false,                // true=用 high 队列, false=用 normal
  "Timer": 1000,                    // TriggerMode=0 时的间隔(ms)
  "TriggerMode": 0,                 // 见下表
  "CooldownCoordX": 0,              // TriggerMode=1 时的冷却图标坐标
  "CooldownCoordY": 0,
  "CooldownSize": 12,               // 冷却图标边长(px)
  "ColorTolerance": 12,             // RGB 容差
  "ExecuteCondition": 0,            // 见下表
  "ConditionCoordX": 0,             // ExecuteCondition!=0 时的检测点
  "ConditionCoordY": 0,
  "ConditionColor": 0,              // 0=资源充足检测, 1=HP红色检测, >1=RGB相似度
  "AltKey": "",                     // ExecuteCondition=2 时备用按键
  "BossOnly": false                  // true=仅 BOSS 模式开启时自动触发(TriggerMode=2 不支持)
}
```

### TriggerMode 枚举

| 值 | 名 | 行为 |
|----|-----|------|
| 0 | **定时** | 按 `Timer` 间隔触发,`Key` 入队 |
| 1 | **冷却检测** | `cooldown_checker_interval` 周期内检测 `(CooldownCoordX, CooldownCoordY)` 区域,匹配度 ≥ 95% 视为就绪,就绪才触发 |
| 2 | **按住** | Python 下发完整期望持键集合,AHK 端声明式账本做差量同步。START/RESUME 声明配置集合,STOP/PAUSE 声明空集合;不经过四级动作队列,详见 wiki/03 |

### BOSS 技能分组

`BossOnly=true` 表示该技能只在运行时 BOSS 模式开启时参与自动触发。BOSS 模式由 `global.boss_mode_hotkey` 切换,每次 START 默认关闭。

限制:
- 只影响 `TriggerMode=0` 定时技能和 `TriggerMode=1` 冷却检测技能。
- `TriggerMode=2` 按住型技能不参与 BOSS 模式。GUI 会禁用这个勾选,配置归一化也会把按住型的 `BossOnly` 清为 `false`。
- BOSS 模式只在 combat 技能模式生效；宏模式和 pathfinding READY 都不注册
  BOSS 热键，避免 `$` Hook 吞掉一个当前没有行为的物理键。

### ExecuteCondition 枚举

| 值 | 名 | 行为 |
|----|-----|------|
| 0 | **无条件** | 直接执行 `Key` |
| 1 | **BUFF 限制**(buff 已存在则跳过) | 检测 `(ConditionCoordX, ConditionCoordY)` 像素 → 若**符合**(buff 在身上)则**不**执行 |
| 2 | **资源条件**(资源足够走主键) | 检测条件 → **符合**走 `Key`,**不符合**走 `AltKey`。带连续 2 帧确认避免抖动 |

### ConditionColor 枚举

| 值 | 含义 |
|----|------|
| 0 | "资源充足"判定:像素 RGB 极差 > `ColorTolerance` 视为资源条满足 |
| 1 | "HP红色"判定:`r>100 && g<50 && b<50` 视为 HP 在场 |
| ≥2 | RGB 相似度:与该数字(0xRRGGBB)比对,容差 `ColorTolerance` |

## global.window_activation

```json
"window_activation": {
  "enabled": true,
  "ahk_class": "Notepad++",         // 优先用类名匹配
  "ahk_exe": "notepad++.exe"        // 进程名(GUI 有"刷新进程列表"按钮)
}
```

`ahk_class` 与 `ahk_exe` 由同一个 `WindowUtils` 目标解析器归一化。只配置一个时按
该条件匹配；两者同时配置时必须由**同一个窗口**同时满足，并把组合 WinTitle
`ahk_class ... ahk_exe ...` 下发给 AHK。DXGI 捕获、可选窗口激活、`ControlSend`
以及寻路点击因此使用同一目标，不再各自选择不同窗口。

两个字段都必须是字符串，且不能含换行或 NUL。显式写入的畸形 selector 会在
READY/坐标点击边界 fail-closed；它与合法的空 selector 严格区分，不能退化成
“使用当前前台窗口”的 direct 兼容路径。

`enabled` 只控制 READY 是否主动激活目标，不会阻止目标选择器同步。`control` 模式或
`enabled=true` 时必须至少配置一个目标条件；`direct` 且禁用自动激活时允许留空，
普通截图会使用当前前台窗口。寻路使用物理鼠标，为防止误点其他应用，额外要求明确
配置目标且目标当前在前台。

## global.input_mode

```json
"input_mode": "direct"
```

| 值 | 含义 |
|----|------|
| `direct`(缺省回退) | AHK 用 `SendInput` 写系统全局输入流；配置目标后，发出新按键/点击时目标必须仍在前台 |
| `control` | 键盘输入用 `ControlSend`、鼠标按钮用 `ControlClick` 向后台目标发送；均覆盖普通按键、宏 down/up 和持久持键(部分游戏不支持) |

由 `AHKCommandSender.set_send_mode(mode)` 在 F8/F9 进 READY 时同步给 AHK。
缺少该字段时运行时回退为 `direct`；仓库当前的 `default.json` 显式写了
`control`，因此“回退默认”不等于“默认配置文件的取值”。
非 `direct`/`control` 枚举、AHK 业务拒绝或传输失败都会使 READY 事务回滚，
不会沿用上一轮的输入模式开闸。

`direct` 并不等于“无条件写当前窗口”：只要配置了 `ahk_class/ahk_exe`，AHK
会在消费队列时持续复核目标；用户切走时拒绝新全局输入，并释放已经在飞的
down/临时 press。只有目标选择器留空时，才保留向当前前台窗口发送的兼容行为。
`control` 必须配置明确目标，并按实际 down 时的 route/target 配对 up。
`mouse_click_at` 是屏幕坐标物理点击，无法用 `ControlSend` 后台化，因此两种
模式下都要求明确目标仍在前台，且坐标位于该前台 HWND 当前客户区内。

`global.process_history.recent_processes` 是 GUI 保存的历史进程名元数据。当前
运行时不靠它选择窗口；实际目标始终以上一节的 `window_activation` 为准。GUI
采集/保存配置时会深拷贝保留该对象，未知的兼容子字段也不会被原地修改。

`global.key_press_duration` 控制普通 `press` 动作从 key-down 到 key-up 的持续时间，
合法范围 `1..1000ms`，默认 `10ms`。Python 在配置同步时下发，AHK 的
direct/control 临时 press 账本统一使用该值；它不控制宏步骤之间的节奏，
步骤间隔必须写显式 `delay`。
若后续显式 `down` 接管同一路由、同一个键，则取消该键原有的临时释放，直到持键
所有者执行 `up` 或安全清理时才释放；不会影响其他键或其他目标的待释放动作。

## global.sequence_enabled / macro_steps

通用宏模式。`sequence_enabled=true` 时,技能模式的定时/冷却任务不运行,Python 只保留 HP/MP 资源检测任务;宏步骤由 AHK 端解释器按顺序循环执行。

```json
"sequence_enabled": true,
"macro_steps": [
  {"type": "down",  "key": "RButton"},
  {"type": "down",  "key": "1"},
  {"type": "up",    "key": "1"},
  {"type": "delay", "ms": 50},
  {"type": "up",    "key": "RButton"}
]
```

步骤类型:

| type | 字段 | 行为 |
|------|------|------|
| `down` | `key` | 直接 `SendDown(key)`,保持按住 |
| `up` | `key` | 直接 `SendUp(key)`,释放 |
| `press` | `key` | `SendPress(key)`,一次点击/按键 |
| `delay` | `ms` | AHK 宏解释器等待指定毫秒 |

当前实现要点:
- `macro_steps` 是权威字段。`skill_sequence` 只作为旧配置迁移/可读性字段保留。
- 非 `delay` 步骤之间没有旧版 `sequence_timer_interval` 的等待;节奏由显式 `delay` 步骤决定。
  AHK 的 5ms 只是轮询预算,会被 Windows timer 粒度量化,不能当作保证的步间隔。
- `press` 步骤自身的 down→up 时长由 `key_press_duration` 控制；这与步骤间的 `delay` 是两个独立维度。
- 宏解释器独立于 4 级队列,不使用队列 `notBefore` 或管理键 `ManagedDelayUntil`,因此 down/up 顺序不受 normal/emergency 队列交错影响。
- PAUSED/STOPPED/配置切换会调用 `STOP_MACRO`,AHK 端按 LIFO 释放宏中仍按住的键。
- 旧 `skill_sequence` 仍可写 `"1,delay100,2"`;加载时会迁移为 `press/delay` 步骤,但无法表达 `down/up`。

## global.boss_mode_hotkey

```json
"boss_mode_hotkey": "XButton2"
```

技能模式下注册为 `intercept` 热键,用于切换运行时 BOSS 模式。每次进入 RUNNING 默认关闭;按一次开启,再按一次关闭。OSD 会显示 `BOSS:开/关`。

BOSS 模式关闭时,`skills.*.BossOnly=true` 的定时/冷却自动技能会被跳过;普通技能照常执行。宏模式和寻路模式不注册此热键。

## global.stationary_mode_config

原地模式 + 强制移动 + 互动。

```json
"stationary_mode_config": {
  "hotkey": "x",                                    // 切换原地模式的热键
  "mode_type": "shift_modifier",                    // 见下表
  "force_move_hotkey": "a",                         // 强制移动键(monitor 模式)
  "force_move_replacement_key": "f",                // 按住 a 期间非白名单/非紧急队列按键替换为 f
  "force_move_passthrough_keys": ["RButton", "space"]  // 白名单:这些键不被替换(位移技能)
}
```

`force_move_passthrough_keys` 字段:强制移动期间**程序自动发出的非紧急按键**若在白名单内,就正常发送;不在白名单内则替换为 `force_move_replacement_key`。典型场景:
- **RButton 闪现/dash**:跑路时仍允许自动/管理逻辑发位移键,不替换成互动键
- **space 翻滚/dodge**:如果你确实希望程序自动发 space 仍保留,显式加入白名单

它和 `priority_keys.special_keys` 不是同一个概念:
- `special_keys` 管的是**用户物理按下该键**时,游戏透传且自动系统让路。
- `force_move_passthrough_keys` 管的是**强制移动期间程序自动发该键**时,是否绕过替换。
- 特殊按键不会自动并入强制移动白名单;需要保留时请显式填写,避免隐藏行为。

匹配在 AHK 端不区分大小写。空列表/缺省 → 强制移动期间非紧急队列键都替换为互动键。HP/MP 紧急药剂由 `IsEmergencyAction` 识别,**永远不被强制移动替换**,避免边跑路边把药剂发成 `f`。

`force_move_hotkey` 和 `priority_keys.special_keys` 都依赖物理 key-up 表示“松开”，因此不能配置为 `WheelUp/WheelDown/WheelLeft/WheelRight`；滚轮只有离散刻度、不会产生可用的 up 边沿，AHK 会拒绝这两种 Hook。滚轮仍可用于 BOSS/原地等 `intercept` 单击动作和 `managed_keys`。

### mode_type 枚举

| 值 | 行为 |
|----|------|
| `shift_modifier`(常用) | 原地模式激活时,所有 `SendPress(key)` 改为 `Send "+{key}"`(Shift+key) |
| `block_mouse` | 原地模式激活时,吞掉自动发送的左右键 `press/down/click`;`release` 仍放行,避免卡键 |

激活命令只接受上述两个值；未知值会被 Python 和 AHK 双端拒绝。切换 profile
时即使新配置为空/未知，也会显式清掉 AHK 缓存的旧 `stationary_type`，不会继承
上一份配置。发送失败时 Python 不先提交本地“已切换”状态，避免两端账本分叉。

### 强制移动 + 互动键(设计意图,**不是 BUG**)

按住已配置的 `force_move_hotkey`(例如 D4 profile 里的 A)期间；
该字段缺省/为空时功能关闭:
1. AHK 端 `ForceMoveActive=true`
2. 非白名单、非 HP/MP 紧急药剂的 `SendPress` 被替换成 `force_move_replacement_key`(默认 `f`)
3. 白名单键和 HP/MP 紧急药剂正常发送;特殊按键是否在白名单内由配置显式决定
4. 效果:角色边强制移动边不停发 `f`,自动捡装备/触发 NPC 对话(D4/PoE2 常用技巧),但仍可位移和喝药

如果你的游戏 `f` 键有别的功能,改 `force_move_replacement_key` 字段。

## global.resource_management

HP/MP 自动药剂。

内部冷却从成功发送药剂命令时开始；未发送过的新动作没有冷却。更换按键或
启用状态会作废该资源的旧冷却，单纯调整检测参数/冷却时长不会获得额外立即使用机会。

```json
"resource_management": {
  "check_interval": 200,            // 资源检查间隔(ms)
  "hp_config": {
    "enabled": true,
    "key": "1",                     // 触发的按键
    "threshold": 50,                // 百分比阈值,< threshold 触发
    "cooldown": 5000,               // 内部冷却(ms),防过快连按
    "detection_mode": "rectangle",  // rectangle | circle | text_ocr

    // detection_mode=rectangle 时
    "region_x1": 100, "region_y1": 800,
    "region_x2": 250, "region_y2": 850,
    "tolerance_h": 10,              // HSV 容差
    "tolerance_s": 30,
    "tolerance_v": 50,

    // detection_mode=circle 时
    "center_x": 175, "center_y": 825,
    "radius": 80,
    "half": "left",                // 可选,只分析哪半边(避开被遮挡侧): left|right|full
                                   //   缺省: HP=left, MP=right (D4 中央球默认)
                                   //   PoE2 角落球: HP=right, MP=left (与默认相反)
    "detect_barrier": true,        // HP 可选:把蓝紫护盾视为安全填充;仅 false 关闭
    "liquid_by_brightness": false, // 可选:忽略色相,改用饱和度/亮度判断液体
    "s_min": 30, "v_min": 25,     // 上项为 true 时生效,有限百分数 0..100

    // detection_mode=text_ocr 时
    "text_x1": 97, "text_y1": 814,
    "text_x2": 218, "text_y2": 835,
    "ocr_engine": "paddle",         // paddle | template | keras | tesseract
    "ocr_model": "PP-OCRv6_small_rec",
    "ocr_device": "cpu",            // cpu | gpu
    "match_threshold": 0.70          // PaddleOCR rec_score 下限
  },
  "mp_config": { ... 同上 ... }
}
```

`half`、`detection_mode` 或 `ocr_engine` 为未知值时都会跳过该资源的本轮判定，
不会偷偷改用另一种检测范围/算法，也不会按“0%”触发药剂。

旧版本配置中的 `hp_config.colors` / `mp_config.colors` 是未接入执行路径的死字段。
当前运行时不会读取，GUI 下次采集/保存也会移除它们；仓库 profile 已不再包含。
GUI 的颜色分析工具只是辅助观察画面和调节 `tolerance_h/s/v`，rectangle/circle
检测的权威输入仍是 F8 缓存的 HSV 模板与这些容差。不要误以为只改 `colors`
就会改变运行期判定。

### detection_mode 枚举

| 值 | 算法 | 速度 | 成功率 | 备注 |
|----|------|------|--------|------|
| `rectangle`(推荐) | HSV 模板 + 有效填充行占比 | **0.262ms/帧（HP+MP）** | 100% 产出；91.2% 的有效对比误差 <5 个百分点 | 适合条形资源条 |
| `circle` | HSV 模板 + 半圆掩码 | 历史估计 ~5ms | 未纳入当前基准 | 适合球形资源条(D4) |
| `text_ocr` | 数字 OCR | 依引擎与计时范围，见下表 | 见下表 | 适合 PoE2 数字显示;PaddleOCR 为当前推荐 |

其中 rectangle/template/keras/tesseract 的数字来自仓库保存的 239 帧（HP+MP
共 478 次识别）历史结果；耗时按每帧完成 HP+MP 两项检测计，不是单项耗时。
circle 与 Paddle 不在当前基准脚本中，不能把其估计值
归因于同一批样本。可复现范围和数据依赖见 wiki/05。

### ocr_engine 枚举

| 值 | 耗时 | 成功产出率（不是标注准确率） | 依赖 |
|----|------|--------|------|
| `paddle`(推荐) | 历史运行估计 CPU ~21ms / GPU ~6ms | 当前脚本未测 | PaddleOCR 3.x + paddlepaddle;F8 READY 阶段校验并锁定用户框选区域、预热模型,运行期 rec-only |
| `template` | ~24.1ms/帧（HP+MP） | 98.3% | 无额外依赖(用预生成数字模板) |
| `keras` | ~96.9ms/帧（HP+MP） | 98.5% | deepai 模块,首次启动加载 ~2s |
| `tesseract` | ~239.6ms/帧（HP+MP） | 99.0% | Tesseract OCR(`tesseract_ocr.tesseract_cmd` 配置路径) |

PaddleOCR 细节:
- `match_threshold` 会传给 `recognize_and_parse(..., min_score=...)`;低于阈值的读数丢弃,避免低置信误采信。
- `match_threshold` 必须是 `0..1` 的有限数；HSV 容差和亮度阈值同样会做有限范围校验。非法值整轮跳过，不会按“0%”触发药剂。
- F8 进入 READY 时,`ResourceManager.lock_ocr_number_position()` 会按当前帧边界校验用户的 `text_x1/y1/x2/y2` 框，锁定该框并预跑一次 rec-only；它不会自动移动或收紧 ROI。
- 运行期如果日志出现 `HP PaddleOCR 数字框未在F8锁定`,说明 READY 阶段没有成功锁框,不会触发该资源动作。
- `text_*` 与 `region_*` 坐标都使用虚拟桌面物理像素的半开区间，`0` 是合法原点；副屏可出现负坐标。负数不是天然非法，只有零面积、或转换到当前 DXGI output 后越界的区域会被拒绝。
- 热更新 Paddle 的启用状态、检测模式、OCR 引擎或 `text_*` 坐标会立即作废旧锁框；为避免用旧区域误判，重新进入 READY 完成锁定前该资源不会触发。

## global.priority_keys

特殊键 + 管理键的高级配置。

```json
"priority_keys": {
  "enabled": true,
  "special_keys": ["space"],         // special 模式 Hook(透传 + 状态监控)
  "managed_keys": {                  // priority 模式 Hook(拦截+映射+延迟,程序代按)
    "e": {
      "target": "shift",             // 把 e 映射成 shift(避免自拦截)
      "delay": 50,                   // 前后各 50ms delay 保证时序
      "hold_ms": 0                   // 可选:>0 时按 hold→delay→release 节奏发,模拟物理按住
    },
    "RButton": {
      "target": "RButton",           // target=自身时,只是为了享受 delay 保护
      "delay": 25
    },
    "c": {
      "target": "c",                 // 大招类:前置 delay 等 LButton 动画收尾
      "delay": 75,
      "hold_ms": 25
    }
  }
}
```

**按键命名约定**: `priority_keys` 的 key 和 `target` 都保存为 AHK 标准按键名。鼠标键使用 `LButton` / `RButton` / `MButton` / `XButton1` / `XButton2`;GUI 可接受 `left_mouse` / `right_mouse` / `x1` / `button8` 等别名输入,但保存前会归一化为 AHK 标准名。按键监听优先用 `pynput`,并有 Qt 本地事件兜底。

### special_keys vs managed_keys

| 属性 | special_keys | managed_keys |
|------|--------------|--------------|
| AHK Hook 模式 | `special`(`~` 前缀) | `priority`(`$` 前缀) |
| 是否拦截 | ❌ 透传给游戏 | ✅ 完全拦截后程序代按 |
| 清非紧急队列 | ❌ 仅过滤(但 `release:*` 与 HP/MP 仍放行,见 `IsAllowedDuringPause`) | ✅ 立即清 |
| 保护期 | 按住期间 + 可选的松开后 `special_key_resume_delay_ms` | delay + hold + delay 窗口 |
| 配置类型 | 字符串列表 | `{ target, delay, hold_ms? }` 对象 |
| 用例 | 闪避(Space) | 闪现 / 强力技 / 大招(RButton/E/C) |

**为什么管理键要 target+delay+hold_ms**:
- `target` 防止 AHK 端的 `$E` Hook 自己拦截自己 SendInput 出来的 `E`
- `delay` 给游戏后摇时间,避免连续技能冲突。**前置 delay 还可以让正在播放的 LButton 自动键动画在 c 大招按下前收尾**,这是 ARPG 大招最重要的语义
- `hold_ms` >0 时把单次 press 改成 `hold:target` → `delay_clear:hold_ms` → `release:target`,模拟物理按住,对要求长按检测的游戏更稳
- 完成时发 `managed_key_complete` 供 Python 记录;AHK 在最后一个管理键完成时自行解除抑制并补齐持久持键,Python 调度器从未暂停

**跨类冲突防御**:同一个 key 不能同时声明在 special_keys 和 managed_keys,Python 注册时检测到重复会 LOG_ERROR 并跳过后注册者(`registered_business_keys` set 跟踪)。

**与强制移动白名单的关系**:`special_keys` 不会自动加入 `stationary_mode_config.force_move_passthrough_keys`。前者只描述用户物理按键时的透传/让路,后者只描述强制移动期间程序自动发键是否被替换。需要同时满足两种语义时,两个字段都显式配置。

### 字面加号键 `target="+"`

如果某个管理键想发字面加号键(`{+}`),AHK 端会正确识别(`StrLen(key)=1` 时认为是字面键,长度>1 且首字符是 `+` 才认为是 Shift 修饰符前缀)。

## global.affix_reroll(初步实现)

装备词缀洗练。F7 触发,`SimpleAffixRerollManager` 跑独立线程。
每次启动创建独立 generation、配置快照、停止事件和 AHK 闸门所有权；超过 join 预算后
才返回的旧 OCR 线程不能点击、关闭新一轮闸门或发布覆盖新状态的 UI 通知。
该模式使用物理屏幕坐标，因此与寻路一样必须在
`window_activation.ahk_class` / `ahk_exe` 中配置明确目标；目标不在前台时拒绝启动或点击。

```json
"affix_reroll": {
  "enabled": false,
  "target_affixes": ["生命", "暴击"],
  "max_attempts": 100,
  "click_delay": 200,
  "enchant_button_coord": [120, 800],
  "first_affix_button_coord": [120, 600],
  "replace_button_coord": [120, 700],
  "close_button_coord": [120, 900]
}
```

`target_affixes` 必须是字符串数组；空白字符串和非字符串项会被丢弃。启动还要求
目标列表非空，并且上述 `enchant_button_coord`、`first_affix_button_coord`、
`replace_button_coord`、`close_button_coord` 四组坐标全部是两个有限 32 位整数；
任一项缺失或畸形都会拒绝启动，而不是在流程中途才误点或失败。

`click_mouse_at(x, y, hold_time=None)` 已通过现有 `CMD_ENQUEUE` 协议下发
`mouse_click_at:x,y,hold_ms`（`hold_time` 沿现有调用约定为毫秒）。AHK 会按
虚拟桌面边界先校验坐标；执行时再要求显式目标仍在前台，并按该前台
HWND 当前客户区的左/上闭、右/下开边界校验坐标。长按使用队列 `notBefore` 安排
不可丢的 `LButton up`，不会用 `Sleep` 阻塞 HP/MP 或其他优先级。
洗练 OCR 不再固定截取主屏 `(0,0,500,h)`：每轮从同一目标 HWND 解析客户区，
截取客户区左侧最多 500px 的虚拟桌面区域，`ImageGrab(all_screens=True)`
支持左/上副屏的负坐标。目标离开前台、窗口失效或客户区不可解析时本轮 fail-closed。

## global.pathfinding_config(初步实现)

自动寻路。F9 准备 pathfinding 模式(STOPPED → READY 并设 `_prepared_mode = "pathfinding"`),按 Z 进入 RUNNING 后 `PathfindingManager` 才启动独立线程开始寻路。

```json
"pathfinding_config": {
  "minimap_area": [1600, 70, 250, 250]    // [x, y, w, h]
```

`pathfinding_config.hotkey` 从未被运行时读取，GUI 加载时忽略、下次保存时移除它；

`minimap_area` 使用虚拟桌面绝对物理坐标，左/上副屏的 x/y 可以为负，
w/h 必须为正。

坐标点击执行链已可用；寻路算法本身仍属于初步实现。移动点击以当前目标窗口
**客户区中心**为原点,不使用固定分辨率坐标；目标窗口不在前台、窗口句柄失效或
客户区无法解析时会安全跳过,不会退回 `(960,540)` 或点击当前其他应用。

## global.tesseract_ocr

```json
"tesseract_ocr": {
  "tesseract_cmd": "D:\\Program Files\\Tesseract-OCR\\tesseract.exe",
  "lang": "eng",
  "psm_mode": 7,                    // 单行文本
  "char_whitelist": "0123456789/"   // 只识别数字和斜杠
}
```

只在 `resource_management.{hp,mp}_config.detection_mode=text_ocr` 且 `ocr_engine=tesseract` 时用到。
运行时和 GUI 的“Text OCR 测试”都读取**当前已加载配置**的这一段，不会暗中读取
`default.json`。加载/保存另一份配置导致签名变化时会安全重建识别器，无需重启程序。
Python 包装 `pytesseract` 由根目录 `requirements.txt` 安装；系统仍需另装
Tesseract 可执行文件，并通过 `tesseract_cmd` 或 PATH 提供。
`psm_mode` 只接受 Tesseract 的 `0..13`；类型错误、非有限值或越界值回退为默认 `7`。
`char_whitelist` 缺省为 `0123456789/`；部分仓库 profile 额外包含逗号，这只是
允许 OCR 输出该字符，后续 `当前值/最大值` 解析仍以数字与斜杠格式为准。

## 时间间隔参数

```json
"capture_interval": 40,             // C++ DXGI 捕获间隔(ms)
"special_key_resume_delay_ms": 0,   // special key 松开后自动输入恢复保护(0..1000ms)
"cooldown_checker_interval": 100,   // 技能冷却检查周期(ms)
"sequence_timer_interval": 1000,    // 旧序列字段保留;当前宏模式不再用它控制步间隔
"check_interval": 200               // (在 resource_management 内) 资源检查周期
```

`sequence_timer_interval` 仅说明旧配置兼容：当前 GUI/默认配置不再生成该字段，
运行时也不读取；旧文件里的值即使因未知字段保留机制继续存在，也没有执行语义。

上例的 `capture_interval=40` / `cooldown_checker_interval=100` 是字段
缺失时的运行时回退值；仓库当前 `default.json` 为实际 profile
显式调优成 55ms / 125ms。`check_interval` 的缺省回退与当前
profile 均为 200ms。

`special_key_resume_delay_ms` 只延迟自动宏、队列和持键恢复;特殊键的物理 key-up 与 `special_key_up` 事件始终立即发生。缺省 `0` 保持立即恢复;`d4_druid.json` 使用 `125ms`,避免高频序列宏复位后立刻发送 LButton 抢占闪避输入。

其他检测间隔调小可以更快响应但 CPU 占用上升。一般保持默认即可。宏模式的等待请在 `macro_steps` 中显式加入 `{"type":"delay","ms":...}`;不要再依赖 `sequence_timer_interval`。

## 配置变更如何同步到 AHK

显式点击“保存配置”时:

1. UI widget 收集 → `ui:save_full_config_requested` 事件
2. `MacroEngine.save_full_config` 先归一化并原子写文件
3. 只有落盘成功后才更新引擎配置、当前文件名并发 `engine:config_updated`
4. `engine:config_save_result` 通知 GUI:成功才更新文件名显示;失败则显示错误并保留旧运行配置
5. 各 manager 订阅 `engine:config_updated`:
   - `SkillManager._apply_config_update` 把 skills/global 作为一个最终状态事务提交，输入成功后才重组调度任务
   - `ResourceManager.update_config` 更新 HP/MP，并按签名同步当前 `tesseract_ocr` 配置
   - `BorderFrameManager._on_config_updated` 更新窗口配置
6. `MacroEngine._on_config_updated` 还会:
   - `set_force_move_key / set_force_move_replacement_key / set_force_move_passthrough_keys` 同步给 AHK
   - `_update_ahk_emergency_keys_cache` 调用 `batch_update_config` 更新 HP/MP 缓存键和 `stationary_type`；禁用资源时显式发送空键以清除 AHK 旧缓存

STOPPED 状态下,物理 F8 和界面启动按钮走同一条 UI 采集链,都会在进入 READY 前执行
`normalize_config_keys`,确保 `xbutton1` 等别名进入运行态前归一成 `XButton1`。
这条 F8 链只更新本次运行配置,不会隐式保存到磁盘；需要持久化时仍应点击“保存配置”。
停止路径不采集 UI 配置,保证 F8 的停机能力不受控件异常影响。

大多数纯调度/资源配置可在运行中收敛，无需重启程序；但动态 Hook、发送模式、
捕获模板和 PaddleOCR 锁框属于 READY 准备快照。修改这些字段后应先进入 STOPPED，
再按 F8/F9 重新完成 READY，不能把一次 `engine:config_updated` 当成所有子系统都已
无条件热重建。

显式点击“加载配置”时采用同样的提交边界:

1. `ConfigManager.load_config` 必须成功解析 JSON,且顶层、`skills`、`global` 都必须是对象
2. 最小结构校验（顶层、`skills`、`global` 必须是对象）和按键归一化成功后,
   MacroEngine 才替换当前运行配置并发布 `engine:config_updated`
3. `engine:config_load_result` 成功后 GUI 才更新当前文件名
4. 文件损坏、I/O 错误或结构错误会显示错误,原运行配置和当前文件名保持不变

## 创建新配置文件的快捷方式

GUI "保存配置" 按钮会弹保存对话框。或手动:

```powershell
Copy-Item -LiteralPath default.json -Destination my_game.json
# 用编辑器调字段
python main.py
# GUI 内"加载配置"选 my_game.json
```

JSON 文件在 GUI 加载时会通过 `ConfigManager.load_config` 严格解析 JSON 语法；
`NaN` / `Infinity` / `-Infinity` 以及 `1e309` 这类解析后溢出的非有限数都会被拒绝，
保存时也不会写出这些非标准 JSON 值。
MacroEngine 再校验上述三段对象结构。当前没有完整 JSON Schema；嵌套字段的范围、
枚举和值类型仍由对应模块在使用时校验或 fail-closed。已覆盖的语法/最小结构错误会
同时写日志并在主窗口弹出提示,不会再静默替换成空配置。
